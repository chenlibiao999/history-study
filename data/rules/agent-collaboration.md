# Agent 协作规则

> 规则编号：COLLAB-001  
> 适用范围：历史学习工作台的内容补充、史实核验、数据维护、界面回归和发布前检查  
> 状态：生效

## 1. 核心原则

1. 复用的是**角色、职责、提示词、规则文档和交付格式**，不是依赖某个已经完成的智能体实例。
2. 子智能体名称由系统生成时，名称只代表一次任务实例，不代表固定身份、长期记忆或永久工作进程。
3. 所有协作角色必须读取本项目的规则池、数据结构说明和当前任务说明；不得只依赖上一次对话中的隐含上下文。
4. 同一批任务默认使用三角色协作。任务规模较小时可以减少角色，但不得因此跳过必要的史实核验或页面回归。
5. 子智能体优先输出审查结果和建议，由主 Agent 统一合并；未经分工确认，不得让多个角色同时改写同一个数据文件。

## 2. 固定三角色

### 2.1 史实与来源审校

- 核对年代、人物、政权归属、事件因果和地理表述。
- 优先使用公开、权威、可追溯的史料或研究资料。
- 标记不确定内容、争议判断和需要补充出处的字段。
- 不负责修改页面布局，不以页面显示正常代替史实核验。

### 2.2 数据与规则校验

- 检查 `event`、`process`、`people`、帝王索引、区域、地图和跨朝代关联是否符合 schema 与规则池。
- 检查事件是否应独立成项，是否错误压缩、重复录入或跨朝代污染。
- 检查符合条件的政权、文明或统一国家是否补充疆域与人口数据。
- 运行项目已有校验脚本，并输出失败项、影响文件和修复建议。

### 2.3 UI 与回归测试

- 检查静态页面能否加载、资源路径是否正确、筛选与搜索是否真实生效。
- 检查时间线、详情页、帝王关联、地图展示、按钮跳转和空状态。
- 检查数据异常是否导致 `[object Object]`、空白页、无限加载或控制台错误。
- 只在任务明确要求时修改前端；发现问题时先提供可复现步骤和影响范围。

## 3. 标准启动流程

每次启动协作任务时，主 Agent 必须向三个角色提供：

1. 当前任务目标和验收标准。
2. `data/rules/`、`data/schema.md` 和相关朝代或区域目录。
3. 已知变更范围、禁止修改的文件和前置假设。
4. 统一的输出格式：`结论`、`问题`、`证据/文件`、`建议动作`、`验证结果`。

三角色完成后，主 Agent 必须：

1. 汇总重复问题，区分事实问题、结构问题和界面问题。
2. 先修复规则或数据结构问题，再修复内容，最后做页面回归。
3. 对每个已采纳结论记录对应文件和验证命令。
4. 将本轮新增的长期规则同步写入对应规则文档，不能只留在聊天记录中。

## 4. 文件修改边界

- 史实审校：默认只读；需要落地时修改对应朝代或区域的数据文件，并保留来源字段。
- 数据与规则校验：可以修改数据、schema 和规则文档，但不得擅自改 UI 样式。
- UI 与回归测试：可以修改前端代码和测试脚本，但不得为了通过页面测试篡改历史数据。
- 同一文件存在多个角色修改需求时，由主 Agent 排队合并，并在合并后重新运行校验。
- 禁止把协作角色临时结论写入永久数据；未核实内容必须标记为待核验。

## 5. 复用策略

### 推荐复用层级

1. **项目规则层**：本文件、`data/rules/`、`data/schema.md`。
2. **角色工作流层**：本文件中的三类固定职责和统一输出格式。
3. **任务上下文层**：同一任务线程中继续推进，以减少重复读取。
4. **智能体实例层**：仅作为一次执行记录，不假设可以长期复用。

### 不采用的方式

- 不通过不断创建新名称来模拟固定团队。
- 不假设历史实例自动保留完整记忆或自动读取最新规则。
- 不让几十个角色并行处理同一批文件，避免重复劳动、冲突修改和无谓的上下文消耗。

## 6. 最小验收清单

- [ ] 三角色职责已明确，且没有两个角色同时拥有同一文件的无序写权限。
- [ ] 三角色均读取了最新规则池和 schema。
- [ ] 史实问题有来源或待核验标记。
- [ ] 数据校验脚本已运行并记录结果。
- [ ] 页面加载、筛选、跳转和关键数据展示已回归。
- [ ] 新增长期规则已同步到对应 `.md` 文档。
- [ ] 主 Agent 已汇总结果并说明未解决风险。

