# 规则同步与变更治理

## SYNC-001 已确认规则必须入文档

- 状态：`active`
- 优先级：最高
- 规则：任何已经确认的规则，必须同步写入对应正式规则文档；不得只存在于聊天记录、任务描述、代码注释或临时脚本中。

## SYNC-002 同步清单

规则变更至少检查：

1. 对应 `data/rules/*.md` 正式文档；
2. `data/schema.md` 数据契约；
3. 对应校验或审计脚本；
4. 数据模板或示例；
5. 当前任务验收标准；
6. Git 提交记录与提交说明。

不适用的同步项必须在任务记录中写明原因。

## SYNC-003 结构化格式

每条正式规则必须包含：

- 唯一编号；
- 状态；
- 适用范围；
- 规则正文；
- 数据或代码影响；
- 审计方式；
- 例外和风险；
- 生效版本或更新时间。

## SYNC-004 权威层级

- 正式规则文档是唯一规范来源。
- `README.md`、`PRODUCT.md`、区域说明和朝代说明只能引用规则，不得单独创造或覆盖强制规则。

## SYNC-005 变更闭环

规则修改必须经过：确认 → 文档更新 → 代码/审计同步 → 任务验收 → 版本记录。未完成闭环的规则标记为 `draft`，不能作为交付依据。

## SYNC-006 文档一致性审计

- 每批规则或数据变更后运行 `node scripts/audit-rule-documentation.js`。
- 该脚本检查正式规则文件和数据契约引用是否存在。
- 脚本通过只代表文档结构完整，不能替代历史数据质量审计。

## SYNC-007 已验收改动直接提交 Git

- 状态：`active`
- 适用范围：所有已完成验证、且用户未明确要求暂缓提交的代码、数据、规则与资源改动。
- 规则：完成约定的校验和页面抽检后，直接创建语义明确的 Git 提交并推送至配置的远端分支；不再等待额外的“提交”或“推送”指令。未经验证、存在阻断错误或仍在讨论中的改动不得提交或推送。
- 数据或代码影响：提交应包含本次已验收改动及其必要规则、校验同步；不得夹带无关的工作区改动。远端推送失败必须明确报告，不得将本地提交误报为已发布。
- 审计方式：提交前运行适用校验与 `git diff --check`；提交后确认工作区仅保留未验收或后续新增改动，并确认远端分支已更新。
- 例外和风险：用户明确要求保留本地改动、拆分提交、暂不提交或改动尚未完成验证时，本规则不执行。
- 生效版本：`2026-08-31`

## SYNC-008 固定工作区

- 状态：`active`
- 适用范围：本项目后续的本地开发、校验和 Git 操作。
- 规则：唯一工作区为 `D:\test\codex work zone\History`；不得在 C 盘日期任务目录或临时目录继续修改本项目。
- 数据或代码影响：所有文件操作、校验、提交和推送均以该目录为仓库根目录。
- 审计方式：执行 Git 或校验命令前确认工作目录为此路径。
- 例外和风险：仅当用户明确指定新的迁移目标时，才允许变更该位置。
- 生效版本：`2026-08-31`
